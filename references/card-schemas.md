# 共享字段与模块连接规范（v2）

这是新库模板、查询和只读检查工具共同遵守的规范。旧库先做字段映射再适配，不能直接套 v2 检查后大规模改名。模板在 [assets/templates](../assets/templates/)；字段名不随中英说明版本改变。

## 1. 公共字段与状态

每份 v2 笔记使用以下公共字段，数组即使为空也写成 `[]`：

```yaml
schema_version: 2
类型: 概念
整理状态: 待整理
核验状态: 待核验
核验日期:
所属专题: []
来源: []
```

- `类型`：配置、导航、概念、规范、案例、专题、产出、反馈、来源。
- `整理状态`：待整理、进行中、已整理、已归档；仅反映编写进度。
- `核验状态`：待核验、部分核验、已核验、待复核、不适用。规范、案例、概念及法律结论类产出不能用“不适用”隐藏依据缺口。
- `核验日期`：实际核验日期（YYYY-MM-DD）；未核验留空，并说明缺口，不填建卡日期冒充核验。
- `来源`：来源定位字符串列表，可为官方 URL、书目与页码、本地文件路径及页码；能够访问且确实核过才称已核验。结构工具不验证网页真伪或法律准确性。
- 不设置通用“已掌握”字段。用途效果记录在反馈卡；整理与核验均不能代替学习成效。

`施行状态`独立于上述两种状态，仅用于规范版本：待核验、现行有效、尚未生效、已废止、已失效、已被取代、草案、不适用。解读、标准或指南应按资料性质说明其地位，不根据标题把它当成强制法律。部分修改注明条款范围；不能仅用“已修订”推断整部文本失效。

## 2. 关联字段的统一格式

`所属专题`、`关联法条`、`关联概念`、`依据卡片` 均为 YAML 字符串列表，值为完整 wikilink：

```yaml
所属专题:
  - "[[某学科知识库/03-专题层/MOC-某专题]]"
关联法条:
  - "[[某学科知识库/01-法规层/某规范-某版本-第X条]]"
关联概念:
  - "[[某学科知识库/03-专题层/概念卡/某概念]]"
依据卡片: []
```

示例只说明语法，不是可原样入库的真实资料。正式值使用**相对整个 vault 的路径**，不带 `.md`、别名或标题锚点；正文可以添加展示别名与段落定位。这样能区分不同学科或不同版本的同名笔记。

字段存在于 frontmatter（文件顶部的 YAML）才可供查询。正文里的“关联法条”标题和双链不能代替字段。专题标题 H1 可自由展示；关联依据是文件路径，不是手动删前缀后的标题字符串。

## 3. 类型要求与粒度

| 类型 | 额外字段 | 正文与关系要求 |
|---|---|---|
| 配置 | 学科、法域、时间范围、学科路径、使用目的、汇总方式 | 已知条件、假设、字段映射、下阶段；使用目的为列表 |
| 导航 | 无 | 范围、问题地图、先修与顺序、已建/计划、入口与缺口 |
| 概念 | 关联法条、关联概念 | 定义依据、自己的解释、边界与反例；连至少一个专题 |
| 规范 | 规范名称、规范性质、条款定位、法域、版本、发布日期、施行日期、施行状态、关联法条 | 原文与解读分开；来源版本及条/款/项定位；关联案例与使用它的卡片 |
| 案例 | 文书编号、作出机关、作出日期、材料类型、程序状态、关联法条、关联概念 | 事实、角色、问题、证据、结论、依据、启示、适用局限；连至少一个专题 |
| 专题 | 关联法条、关联概念 | 核心问题、明确成员链接、争议/缺口、产出和相邻专题 |
| 产出 | 使用目的、交付形式、依据卡片、关联法条、关联概念 | 各项结论对应依据；实际事实与假设分开；验收口径 |
| 反馈 | 使用目的、反馈状态、反馈来源、反馈日期、依据卡片 | 观察、证据、缺口、影响、修订与再检查 |
| 来源 | 无 | 作者/机关、定位、版本、材料性质、可支持结论与待核项 |

规范可为全文或必要的条/款卡，不设“少于多少条必须整部一卡”阈值。案例编号不明时留空并记录原因，不能填假案号。法院与行政机关共用文书编号/作出机关/作出日期作为聚合字段，另按需增加案号、审级、处罚类型等专属字段。指导性案例、参考案例、通报和二手摘要的性质明确记在材料类型。

产出 `依据卡片` 非空，并在正文标明卡片究竟支持哪项结论；有关联不等于依据充分。反馈卡的 `依据卡片` 指向被反馈的产出或知识卡。`反馈状态` 为待反馈、已记录、已修订、已验证；后两者应有实际变更或验证证据。

## 4. 可点击的基础索引与可选 Dataview

始终保留专题成员清单和规范的反向引用清单。新建或调整成员的同一批操作中更新清单；这样没有插件也可使用。正式笔记保留模板中“关联笔记”或“反向引用”区域，并在其中填入对应成员/引用者的明确链接。

已启用 Dataview 才追加以下代码。替换 `{{subject_path}}` 为真实 vault-relative 子库路径；若整个 vault 就是该学科，DQL 使用 `FROM ""`。路径包含双引号/反斜杠时按 DQL 转义。模板本身不预置依赖插件的代码。

专题汇总（字段读取的是链接对象）：

````markdown
```dataview
TABLE 类型, 核验状态
FROM "{{subject_path}}"
WHERE contains(所属专题, this.file.link)
SORT file.name ASC
```
````

规范反查案例：

````markdown
```dataview
TABLE 文书编号, 作出机关, 作出日期, 核验状态
FROM "{{subject_path}}"
WHERE 类型 = "案例" AND contains(关联法条, this.file.link)
SORT 作出日期 DESC
```
````

任意知识卡反查使用它的产出/反馈：

````markdown
```dataview
TABLE 类型, 使用目的, 核验状态
FROM "{{subject_path}}"
WHERE contains(依据卡片, this.file.link)
SORT file.name ASC
```
````

没有 Dataview：只用已维护的显式清单，无须安装插件。元数据与清单须同时保持。普通 Markdown 链接适用于外部来源；库内关联统一用 wikilink。

查询语法参考：[Dataview 表达式与字段](https://blacksmithgu.github.io/obsidian-dataview/reference/expressions/)、[contains 函数](https://blacksmithgu.github.io/obsidian-dataview/reference/functions/#containsobjectliststring-value)。实际渲染仍以目标库的插件环境验证为准。

## 5. 适配旧库

先记录旧字段到 v2 语义的映射，例如案号→文书编号、审理法院→作出机关、裁判日期→作出日期，但不要求重命名旧字段。旧式 `所属专题: [专题名称]` 与链接对象不是同一种值，查询不能混用字符串与 `this.file.link`。

可选做法：
- 沿用旧字段和值类型，针对该库重写查询；正文链接补齐，现有成员不要丢失。
- 用户要求迁移时，备份受影响文件，改写元数据/双链/查询/索引，逐批验证。

无论采用哪种做法，都检查案例→规范、规范→案例、成员→专题、专题→成员、产出→依据。v2 工具只对采用本规范的范围运行；不宣称旧库已经自动修好。

## 6. 模板渲染与检查

`{{title}}`、`{{subject}}`、`{{subject_path}}`、`{{jurisdiction}}`、`{{time_scope}}` 是由执行者替换的参数，不依赖 Templater。按 YAML/Markdown 上下文正确转义；未选用模板不必复制。放进 `99-Templates` 的模板可保留参数，正式笔记不可以。

从对应模板填入真实正文和关联，不把提示语当成已完成内容。原文访问失败时写明缺口；草稿可留待核，不能以“为了通过检查”而填伪造来源。运行 `scripts/validate_vault.py` 检查本规范结构，再人工核验来源、结论和界面查询。
